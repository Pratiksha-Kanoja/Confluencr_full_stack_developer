# Business Logic & Technical Assumptions

This document outlines the key architectural, business logic, and operational assumptions made during the design and implementation of the **Transaction Ledger System**.

---

## 1. Monetary Precision & Currency Representation

* **Integer Cents Representation**: In enterprise banking and financial ledger systems, floating-point representations (`IEEE 754`) introduce binary rounding errors (e.g., `0.10 + 0.20 = 0.30000000000000004`). To ensure absolute mathematical precision, all monetary values are stored in the database as integer cents (`balance_cents`, `amount_cents`).
* **Input Validation**: All incoming `amount` parameters are validated using regex (`/^\d+(\.\d{1,2})?$/`) and positive range checks (`amount > 0`). Fractional cents (e.g., `$10.999`) are rejected with `400 Bad Request`.
* **Database Check Constraints**: SQLite schema defines `CHECK(balance_cents >= 0)` and `CHECK(amount_cents > 0)`. This guarantees at the database storage engine layer that an account balance can never drop below zero, regardless of concurrency race conditions.
* **API Formatting**: For client convenience, responses format cents back to standard decimal numbers (`amount_cents / 100`).

---

## 2. Account Creation & Initial Balance Security

* **Zero Initial Balance Enforcement**: As specified in the assessment requirements, initial balance must always start at `0.00`.
* **Client Tampering Protection**: If a client provides `balance` or `initial_balance` in the payload of `POST /api/accounts`, the request is strictly rejected with `400 Bad Request` rather than silently ignored. This alerts client developers to adherence with financial protocol.
* **Unique Account Identifier**: Account IDs are generated server-side using standard `UUID v4` to guarantee global uniqueness.

---

## 3. Transaction Idempotency & Reference ID Scope

* **Per-Account Uniqueness**: As required, `reference_id` must be unique **within the scope of an account**. This is enforced via an explicit composite unique constraint: `UNIQUE(account_id, reference_id)`.
* **Cross-Account Reusability**: The same `reference_id` may legally be used across multiple distinct accounts (e.g., external vendor invoice numbers, recurring subscription IDs, or batch payroll IDs).
* **Duplicate Detection**: Attempting to insert a transaction with a previously recorded `reference_id` on the same account returns `409 Conflict` (`DUPLICATE_TRANSACTION`). No transaction is created, and the balance remains unchanged.

---

## 4. Transaction Immutability & Audit Trail

* **Append-Only Ledger**: Once created, transactions cannot be modified, edited, or deleted. The API provides no `PUT`, `PATCH`, or `DELETE` endpoints for transaction resources.
* **Foreign Key Protection**: `FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT` ensures that accounts with recorded transactions cannot be deleted.
* **Audit Trail**: Every transaction records an immutable ISO 8601 timestamp (`created_at`) generated by the server clock.

---

## 5. Atomicity & Concurrency Model

* **ACID Transactions**: Every transaction creation, balance deduction, and fund transfer is executed within an explicit SQLite transaction:
  ```sql
  BEGIN IMMEDIATE;
  -- Balance validation & balance update
  -- Transaction record insertion
  COMMIT;
  ```
* **Write Reservation**: Using `BEGIN IMMEDIATE` acquires a write lock before executing queries, preventing read-modify-write race conditions and write starvation.
* **Guaranteed Rollback**: If any validation, constraint check, or query fails, `ROLLBACK;` is executed immediately. No intermediate state is ever persisted.

---

## 6. Money Transfer Protocol (Bonus Feature)

* **Dual-Entry Ledger Posting**: A transfer between Account A and Account B is executed as a synchronized dual-entry operation:
  1. Verify both accounts exist.
  2. Verify Account A has sufficient balance (`balance_cents >= amount_cents`).
  3. Verify Account A and Account B are not identical.
  4. Atomically debit Account A and insert a debit transaction (`TRF-OUT-<reference_id>`).
  5. Atomically credit Account B and insert a credit transaction (`TRF-IN-<reference_id>`).
  6. Insert an audit record in the `transfers` table.
* **No Partial Transfers**: If any step in the sequence fails, the entire transaction is rolled back. A state where money leaves Account A without reaching Account B is strictly impossible.

---

## 7. Pagination and Querying

* **Default Values**: When `page` or `limit` is omitted, defaults are `page = 1` and `limit = 10`.
* **Bounds**: `limit` is constrained to a maximum of `100` to prevent database memory exhaustion.
* **Sorting**: Transactions are sorted strictly in descending order of creation (`ORDER BY created_at DESC`).
* **Filtering**: Filtering by `type` supports `credit`, `debit`, or all (when omitted).

---

## 8. API Compatibility & Routing

* All endpoints are accessible both with `/api/` prefix (e.g. `/api/accounts`) and directly (e.g. `/accounts`) for maximum compatibility with varied client conventions and automated testing tools.
